## 1. ชั้นป้องกันที่มีอยู่

| ชั้น | อยู่ที่ไหน | กันอะไร |
|---|---|---|
| Content-Security-Policy พร้อม nonce | `src/lib/security-headers.ts` + `src/proxy.ts` | สคริปต์แปลกปลอมที่หลุดเข้าไปในหน้า |
| หัวข้อความปลอดภัยพื้นฐาน | `src/lib/security-headers.ts` + `next.config.ts` | clickjacking, MIME sniffing, การรั่วของ referrer |
| กรอง URL ก่อนใส่ `href` | `src/lib/external-link.ts` | stored XSS จากช่องกรอกลิงก์ในหลังบ้าน |
| เพดานการเดารหัสผ่าน | `src/lib/rate-limit.ts` + `src/auth.ts` | brute force บัญชีหลังบ้าน |
| เพดานการส่งฟอร์มสาธารณะ | `src/lib/rate-limit.ts` | สแปมรีวิวและคำขอ |
| ตรวจสิทธิ์ทุก server action | `src/server/cms-helpers.ts` | การเรียก action ตรงโดยไม่ผ่านหน้าเว็บ |
| ตั๋วอัปโหลดที่เซ็นแล้ว | `src/lib/r2.ts` + `src/server/media-actions.ts` | การเขียนข้อมูลไฟล์ปลอมลงคลัง |

### CSP — ด่านสุดท้ายเมื่อมีสคริปต์หลุดเข้าไปแล้ว

`src/proxy.ts` สุ่ม nonce ใหม่ทุกคำขอ แล้วส่งไปสองทาง:
ทาง **response** ให้เบราว์เซอร์รู้ว่าจะเชื่อสคริปต์ตัวไหน
และทาง **request** เพราะ Next อ่าน nonce จากหัวข้อ `Content-Security-Policy` ของคำขอ
เพื่อไปแปะให้แท็กสคริปต์ที่ตัวมันแทรกเอง — ถ้าส่งแค่ทาง response หน้าเว็บจะไม่ทำงานทั้งหน้า

next-intl เป็นคนสร้าง response ของหน้าสาธารณะเอง เราจึงไม่ได้สร้าง response ใหม่ทับ
แต่ไปต่อท้ายสารบัญ `x-middleware-override-headers` ที่มันสร้างไว้แล้ว (ดู `forwardRequestHeaders`)
ถ้าสร้างทับ rewrite ของภาษาจะหายไปทั้งหมด

นโยบายเป็นแบบ `strict-dynamic` ตามที่ Google แนะนำ:
เบราว์เซอร์รุ่นใหม่เชื่อเฉพาะสคริปต์ที่มี nonce ตรงกัน แล้วส่งต่อความเชื่อให้สคริปต์ที่ตัวมันโหลดตามมา
ส่วน `'unsafe-inline'` กับรายชื่อโฮสต์ที่ใส่ไว้ เบราว์เซอร์รุ่นใหม่จะมองข้าม —
มีไว้ให้รุ่นเก่าที่ไม่รู้จัก nonce ยังเปิดเว็บได้ ไม่ใช่ช่องโหว่

**ผลข้างเคียงที่ตั้งใจ:** ทุกหน้ากลายเป็น dynamic รวมถึง `/privacy` และ `/terms` ที่เคย prerender
HTML ที่ prerender ไว้ตอน build จะมี nonce ของตอนนั้นค้างอยู่ ไม่มีทางตรงกับค่าที่สุ่มใหม่ทุกคำขอ
แล้วเบราว์เซอร์จะบล็อกสคริปต์ทั้งหน้า สองหน้านั้นเป็นเนื้อหาสั้น ๆ การเรนเดอร์สดจึงแทบไม่มีต้นทุน

### สิ่งที่ CSP เปิดไว้ และเหตุผล

- `style-src 'unsafe-inline'` — React เขียน style ลงบน attribute โดยตรงหลายจุด และ next/font แทรก `@font-face` มาในหน้า
  ปิดตรงนี้แล้วหน้าเว็บจะพังทั้งเว็บ ส่วนความเสี่ยงของการฉีด style ต่ำกว่าการฉีดสคริปต์มาก
- `img-src https:` — รูปมาจาก R2, YouTube และ placeholder ตอน seed
  รายชื่อโฮสต์ที่แน่นอนอยู่ใน `next.config.ts` (`images.remotePatterns`) ซึ่งเป็นด่านที่บังคับใช้จริงกับ image optimizer
- `connect-src https://*.r2.cloudflarestorage.com` — เบราว์เซอร์ PUT ไฟล์เข้า R2 ตรง ๆ ปิดแล้วอัปโหลดไม่ได้ทั้งระบบ

## 2. ที่แก้รอบนี้

### ยกระดับ Next.js 16.1.1 → 16.3.4

`npm audit` รายงาน **critical สองรายการที่เป็น unauthenticated RCE** และอีกหลายสิบรายการ ที่กระทบตรงกับสถาปัตยกรรมของเว็บนี้:

| ระดับ | เรื่อง | ทำไมถึงกระทบเรา |
|---|---|---|
| critical | RCE บนเซิร์ฟเวอร์ที่รันบน Windows | — |
| critical | RCE ใน Image Optimization API เมื่อมีไฟล์ AVIF | `next.config.ts` เปิด `formats: ['image/avif', ...]` |
| high | Middleware / Proxy bypass ใน App Router (หลายรายการ) | ด่าน `/admin` ทั้งหมดยืนอยู่บน `src/proxy.ts` |
| moderate | null origin ข้าม CSRF check ของ Server Actions | ทั้งเว็บใช้ server action เป็นทางเขียนข้อมูลทางเดียว |
| moderate | XSS ใน App Router ที่ใช้ CSP nonce | ตรงกับสิ่งที่เพิ่งเพิ่มเข้าไปรอบนี้พอดี |

เหลือ 4 high ที่ยังไม่แก้ ทั้งหมดอยู่ใน `prisma` CLI (`@prisma/config`, `deepmerge-ts`, `mysql2`)
ซึ่งเป็น devDependency ที่รันตอน migrate เท่านั้น ไม่ได้ถูกโหลดเข้า runtime ของเว็บ
และ `mysql2` ไม่เคยถูกเรียกเลยเพราะเราต่อ Postgres ทางออกเดียวที่ npm เสนอคือถอย Prisma กลับไปเวอร์ชัน 6 ซึ่งแลกไม่คุ้ม

### stored XSS ในหน้าผลงาน

`src/app/[locale]/work/[slug]/page.tsx` เรนเดอร์ `href={project.liveUrl}` และ `href={project.repoUrl}`
โดยไม่ตรวจ scheme — เป็นปัญหาชุดเดียวกับที่แก้ไปแล้วในฟุตเตอร์และหน้าติดต่อ แต่ตอนนั้นตรวจไม่ครบ

บัญชีระดับ EDITOR พิมพ์ `javascript:...` ลงช่อง "ลิงก์เว็บไซต์จริง" ในหน้าแก้ไขผลงานได้ตามปกติ
แล้วมันจะกลายเป็นปุ่มที่รันสคริปต์ในเบราว์เซอร์ของผู้เข้าชม

แก้สองชั้น: กรองด้วย `safeExternalUrl` ตอนเรนเดอร์ (ครอบระเบียนเก่าที่บันทึกไว้ก่อนหน้านี้ด้วย)
และปฏิเสธตั้งแต่ตอนบันทึกใน `saveProject` กับ `saveSettings` เพื่อให้คนกรอกรู้ทันทีว่าพิมพ์ผิด

### เพดานกันสแปมที่เลี่ยงได้ด้วย header เดียว

`getClientIpHash()` เดิมอ่าน `x-forwarded-for` **ตัวแรก** ซึ่งเป็นค่าที่ผู้เรียกแนบมาเองได้ทั้งหมด
ใครก็ตามที่ส่ง `X-Forwarded-For: <สุ่มใหม่ทุกครั้ง>` จะได้ `ipHash` ใหม่ทุกครั้ง
เพดาน 3 รีวิว/วัน และ 5 คำขอ/ชั่วโมง จึงไม่มีผลกับคนที่ตั้งใจจะเลี่ยง

ตรรกะย้ายไปอยู่ที่ `src/lib/client-ip.ts` เป็นฟังก์ชันบริสุทธิ์ที่เทสต์ได้ตรง ๆ

**โดเมนจริงอยู่หลัง Cloudflare อยู่แล้ว** ตรวจตอนแก้: `alexan.studio` ชี้ไปที่ `172.67.145.97`
กับ `104.21.63.108` ซึ่งเป็นช่วงของ Cloudflare และ response มี `Server: cloudflare` กับ `CF-RAY` ติดมา
สายจริงจึงเป็น ผู้ใช้ → Cloudflare → Railway → container ไม่ใช่ Railway ชั้นเดียว

ตอนแรกเขียนให้นับจากท้ายสาย `x-forwarded-for` โดยตั้งค่าเริ่มต้นเป็น 1 ชั้น ซึ่ง **ผิดกับของจริง**
และผิดในทางที่แย่กว่าการเลี่ยงเพดานเสียอีก: ตัวท้ายสายคือ IP ของ edge Cloudflare
ที่ผู้เข้าชมทุกคนใช้ร่วมกัน ทุกคนจึงได้ `ipHash` เดียวกัน แล้วคนที่หกที่ส่งฟอร์มในชั่วโมงนั้น
จะถูกปฏิเสธทั้งที่ไม่ได้ทำอะไรผิด

แก้โดยอ่าน `cf-connecting-ip` เป็นอันดับแรก Cloudflare เป็นคนเขียนหัวข้อนี้เอง
และเขียนทับค่าที่ผู้เรียกแนบมาเสมอ จึงไม่ต้องนับชั้น proxy ให้ถูกก่อนถึงจะใช้ได้ —
ซึ่งเป็นตัวเลขที่ผิดง่ายและผิดแบบเงียบ ๆ ไม่มีอะไรเตือน

`TRUSTED_PROXY_HOPS` ยังอยู่แต่ไม่ได้เป็นตัวหลักอีกแล้ว เป็นทางถอยสำหรับกรณีที่ไม่มี `cf-connecting-ip`
ถ้าวันหนึ่งถอด Cloudflare ออกเหลือ Railway ล้วน ๆ หัวข้อนั้นจะหายไปเอง
แล้วโค้ดจะตกไปนับ `x-forwarded-for` ด้วยค่าเริ่มต้น 1 ซึ่งถูกต้องสำหรับสายนั้นพอดี — ไม่ต้องกลับมาแก้อะไรตาม

> **ข้อจำกัดที่รับไว้:** ถ้ามีคนหาที่อยู่ origin ของ Railway เจอแล้วยิงตรงโดยไม่ผ่าน Cloudflare
> เขาแต่ง `cf-connecting-ip` เองได้ แต่ในสถานการณ์เดียวกันเขาก็แต่ง `x-forwarded-for` ได้อยู่แล้ว
> การเชื่อหัวข้อนี้ก่อนจึงไม่ได้เปิดช่องอะไรเพิ่มจากเดิม ทางปิดจริงคือล็อก origin ให้รับเฉพาะ Cloudflare
> ซึ่ง Railway ยังทำไม่ได้ตรง ๆ

### หน้าล็อกอินไม่มีเพดานอะไรเลย

เดิมยิงรหัสผ่านเข้ามาได้ไม่จำกัด ตอนนี้นับสองแกนพร้อมกันใน 15 นาที:
10 ครั้งต่อบัญชี และ 20 ครั้งต่อ IP

เลือกเป็น "ชะลอชั่วคราว" ไม่ใช่ "ล็อกบัญชีถาวร" เพราะการล็อกถาวรเปิดช่องให้ใครก็ได้
ยิงรหัสผิดใส่อีเมลของทีมจนทุกคนเข้าระบบไม่ได้ — กลายเป็นเครื่องมือปิดเว็บเสียเอง
และครั้งที่ถูกบล็อกไว้แล้วจะไม่ถูกบันทึกซ้ำเป็นความล้มเหลว ไม่งั้นคนที่ยิงไม่หยุดจะต่ออายุการบล็อกได้เรื่อย ๆ

ด่านอยู่ใน `authorize()` ของ `src/auth.ts` ไม่ใช่ในฟอร์ม เพราะฟอร์มไม่ใช่ทางเดียวที่เข้ามาถึงได้ —
ใครก็ POST เข้า `/api/auth/callback/credentials` ตรง ๆ ได้ ส่วนในฟอร์มตรวจซ้ำเพื่อบอกเหตุผลจริงให้คนที่กรอก

ตาราง `LoginAttempt` เก็บเฉพาะ hash ของอีเมลและ IP ที่ผสม `AUTH_SECRET` แล้ว ย้อนกลับไม่ได้
migration อยู่ที่ `prisma/migrations/20260910120000_login_attempt/`

### บัญชีที่ถูกปิดไปแล้วยังใช้งานได้ต่ออีก 8 ชั่วโมง

session เป็น JWT ที่ลงนามไว้แล้ว มีอายุ 8 ชั่วโมง และ `requireEditor()` เดิมอ่านแต่ค่าใน token
ปิดบัญชีหรือลดสิทธิ์ใครไปแล้ว เขายังถือ token ใบเดิมที่บอกว่าเป็น ADMIN เข้ามาสั่งงานได้จนกว่าจะหมดอายุ
ซึ่งยาวเกินไปสำหรับกรณีที่ต้องตัดสิทธิ์ทันที เช่น คนออกจากทีม

ตอนนี้ `getActiveUser()` อ่านจากฐานข้อมูลทุกครั้ง เช็ค `isActive` และใช้ `role` ตัวจริง ไม่ใช่ค่าใน token
ใช้ตัวเดียวกันทั้ง server action ของ CMS, action ของหลังบ้าน, layout ของ `(panel)` และหน้าพิมพ์ใบเสนอราคา
(`src/server/admin-actions.ts` เคยมีด่านของตัวเองที่อ่านแต่ session — ยุบมารวมแล้ว)

### จุดอื่นที่เก็บไปด้วย

- **หน้าพิมพ์ใบเสนอราคา** `/admin/print/quote/[id]` อยู่นอก `(panel)` จึงไม่ได้รับด่านของ layout นั้น
  เดิมพึ่ง middleware อย่างเดียว ทั้งที่ในหน้ามีชื่อ ที่อยู่ และยอดเงินของลูกค้าเต็มหน้า — เพิ่มด่านตรงจุดที่ดึงข้อมูลแล้ว
- **ตั๋วอัปโหลด** `confirmUpload` เดิมรับ `url` จากเบราว์เซอร์แล้วเก็บลงฐานข้อมูลตรง ๆ
  ตอนนี้เซ็น `key|ชนิดไฟล์|ขนาด` ด้วย `AUTH_SECRET` ตอนออกตั๋ว แล้วคำนวณ url จาก key ที่เซ็นไว้เอง
- **id วิดีโอ** ที่แกะจากลิงก์ถูกต่อเข้า `src` ของ iframe ตรง ๆ — จำกัดให้เหลือเฉพาะชุดอักขระของ id จริง
- **`/api/health`** เดิมบอกคนนอกว่าตั้งค่าที่เก็บไฟล์กับอีเมลไว้หรือยัง และฐานข้อมูลใช้เวลาตอบเท่าไหร่
  ซึ่งเป็นแผนที่ให้คนที่กำลังสำรวจ — ย้ายไปอยู่ใน log ของ container แล้ว เหลือตอบแค่ `status`
- **`bodySizeLimit` ของ server action** ตั้งเป็น 512kb ไฟล์ทั้งหมดไม่ผ่านเซิร์ฟเวอร์ Next อยู่แล้ว
  ที่วิ่งผ่าน action จึงมีแต่ข้อความจากฟอร์ม
- **open redirect ของหน้าล็อกอิน** เดิมตรวจแค่ `startsWith('/admin')` เปลี่ยนเป็นเทียบขอบเขตของ path จริง

### สิ่งที่ต้องปิดไว้ที่ Cloudflare — ไม่ได้อยู่ในโค้ด

**Email Address Obfuscation ต้องปิด** (Security → Settings → กรอง Client-side abuse)
ปิดไปแล้วเมื่อ 10 กันยายน 2026 หลังเจอปัญหาจริงบนโปรดักชัน

ฟีเจอร์นี้แก้ HTML ที่เซิร์ฟเวอร์เราส่งออกไป เปลี่ยนอีเมลเป็น `[email protected]`
แล้วแทรกสคริปต์ `email-decode.min.js` มาถอดรหัสทีหลัง เกิดปัญหาสองชั้นที่ไม่เกี่ยวกันเลย:

1. **hydration พังทุกหน้า (React #418)** — Cloudflare แก้เฉพาะ HTML แต่ไม่แตะ RSC payload
   ที่ React ใช้ hydrate ผลคือ DOM บอกอย่าง payload บอกอีกอย่าง React จึงทิ้งของที่เซิร์ฟเวอร์
   เรนเดอร์มาแล้วเรนเดอร์ใหม่ทั้งต้นในเบราว์เซอร์ — เสียประโยชน์ของ SSR ทั้งเว็บทั้งที่จ่ายค่าเรนเดอร์ไปแล้ว
   (อาการนี้มีมาตั้งแต่ก่อนใส่ CSP)
2. **CSP บล็อกสคริปต์ถอดรหัส** — `strict-dynamic` เชื่อเฉพาะสคริปต์ที่มี nonce
   ตัวที่ Cloudflare แทรกทีหลังไม่มี nonce จึงถูกบล็อก คนที่ไม่รัน JS เลยเห็น `[email protected]` ค้างอยู่

**ทำไมไม่แก้ด้วยการผ่อน CSP:** ผ่อนไม่ได้ — `strict-dynamic` ปิดการอนุญาตด้วยรายชื่อโฮสต์ทั้งหมด
ต้องถอด `strict-dynamic` ทิ้งซึ่งทำให้ CSP อ่อนลงมากเพื่อแลกกับฟีเจอร์ที่กันบอตเก็บอีเมลไม่ได้จริงอยู่แล้ว

**ถ้าวันหลังมันกลับมาเปิดเอง** (ย้าย account, สร้าง zone ใหม่ — Cloudflare เปิดให้อัตโนมัติตอนสมัคร)
อาการที่จะเห็นคือ console มี CSP violation ของ `cdn-cgi/scripts/.../email-decode.min.js`
และ React error #418 ทุกหน้า ทางแก้ถาวรอีกทางคือส่ง header `Cache-Control: no-transform`
จาก `src/proxy.ts` ซึ่งสั่งไม่ให้ Cloudflare แก้ HTML ของเราทุกแบบ ไม่ใช่แค่อีเมล

---

## 3. ที่ตรวจแล้วไม่พบปัญหา

- **SQL injection** — ทุกคิวรีผ่าน Prisma มี `$queryRaw` ที่เดียวคือ `SELECT 1` ใน health check ซึ่งไม่มีค่าจากผู้ใช้
- **XSS จากเนื้อหา Markdown** — `src/components/ui/Prose.tsx` ใช้ react-markdown ซึ่งกรอง scheme ของลิงก์ให้เอง ไม่ได้ใช้ `dangerouslySetInnerHTML`
- **JSON-LD** — `src/components/JsonLd.tsx` หนี `<` เป็น `\u003c` แล้ว ปิดแท็ก `</script>` ก่อนกำหนดไม่ได้
- **การรั่วของเวลาตอบตอนล็อกอิน** — เทียบ bcrypt เสมอแม้ไม่เจอผู้ใช้ จับเวลาแล้วเดาไม่ได้ว่าอีเมลไหนมีอยู่จริง
- **ข้อความ error ตอนล็อกอิน** — ไม่แยกว่าอีเมลผิดหรือรหัสผ่านผิด
- **honeypot ของฟอร์มสาธารณะ** — บอตที่กรอกช่องซ่อนจะได้คำตอบว่าสำเร็จ แต่ไม่มีอะไรถูกบันทึก
- **รีวิวจากคนนอก** — เข้าคิว `PENDING` เสมอ ไม่ขึ้นหน้าเว็บจนกว่าจะอนุมัติ

## 4. ที่ยังเหลือ

- **HSTS ยังไม่ใส่ `preload`** ตั้งใจ — ถอนชื่อออกจากลิสต์ที่ฝังมากับเบราว์เซอร์ใช้เวลาเป็นเดือน
  ค่อยเติมเมื่อมั่นใจว่าทุก subdomain พร้อม https ถาวรแล้ว
- **ยังไม่มีปลายทางรับรายงาน CSP** (`report-uri` / `report-to`) จึงไม่รู้ว่ามีอะไรถูกบล็อกในเบราว์เซอร์ของผู้ใช้จริงบ้าง
- **ยังไม่มี 2FA ของหลังบ้าน** ตอนนี้พึ่งรหัสผ่านอย่างเดียว
- **`prisma` CLI ยังมีช่องโหว่ระดับ high 4 รายการ** (ดูเหตุผลที่รับไว้ในหัวข้อ 2)
- **ยังไม่ได้ยิงทดสอบจริงกับ R2** ตั๋วอัปโหลดที่เซ็นแล้วตรวจด้วยการอ่านโค้ดและเทสต์ระดับฟังก์ชัน
  ยังไม่ได้อัปโหลดไฟล์จริงผ่านโดเมน production
- **`LoginAttempt` จะมีจริงในฐานข้อมูลเมื่อ deploy รอบถัดไป** (`Dockerfile` สั่ง `prisma migrate deploy` ก่อนสตาร์ต)
  ระหว่างนี้โค้ดจับ error แล้วปล่อยผ่าน — ล็อกอินยังทำงานปกติ แต่ยังไม่มีเพดาน
  ถ้าอยากให้มีผลก่อนหน้านั้น รันจากเครื่องตัวเอง: `npm run db:deploy`
- **ยังไม่ได้ยืนยันสายของ header กับ production จริง** สรุปว่าอยู่หลัง Cloudflare จาก DNS และ response header
  ของโดเมน ยังไม่ได้อ่านค่า `cf-connecting-ip` ที่ container เห็นจริง ๆ
  หลัง deploy ถ้าเพดานกันสแปมทำงานผิดปกติ (บล็อกเร็วเกินไปแบบทั้งเว็บพร้อมกัน) ให้สงสัยจุดนี้ก่อน
